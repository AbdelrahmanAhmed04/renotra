# Project explanation

## Architecture in plain language

The browser loads one `index.html`. A small JavaScript router reads the URL, renders the matching page, intercepts internal links, updates browser history, and supports Back/Forward navigation. Firebase Hosting rewrites direct requests to `index.html`, so refreshing `/cars/nissan-sunny-2024` works.

HTML is generated by page and component modules with semantic landmarks, forms, labels, headings, and links. CSS provides the visual system, grid layouts, mobile navigation, states, and reduced-motion support. JavaScript handles routing, form validation, filtering, authentication state, Firestore queries, and live price estimates.

## Firebase responsibilities

- **Authentication** securely manages email/password credentials and sessions. Passwords never enter Firestore.
- **Cloud Firestore** stores the public vehicle catalogue, permitted profile details, and owner-private booking requests.
- **Security Rules** are the real authorization layer. UI redirects improve experience but are not treated as security.
- **Local Emulator Suite** makes signup, persistence, and rules testable without cloud credentials or paid services.

## Collections

`cars/{carId}` contains publish state, model data, daily price, images, features, and ordering. IDs such as `toyota-corolla-2024` are deterministic.

`users/{uid}` contains `displayName`, `email`, `phone`, and timestamps. The document ID must equal the signed-in Firebase UID.

`users/{uid}/bookings/{bookingId}` stores ownership, the selected car ID, name/rate/currency snapshots, ISO date-only strings, UTC-derived calendar days, estimated total, customer contact values, location, status, and timestamps.

## Booking sequence

1. A user chooses a published Firestore car.
2. The booking form validates contact data and dates (today or later, return after pickup, maximum 30 days).
3. Calendar days use UTC arithmetic so daylight-saving transitions cannot change the total.
4. A draft is held in `sessionStorage`, allowing a guest to review and then log in without losing it.
5. Checkout shows all details and contains no card fields.
6. On submission, the app re-fetches the published car, recalculates days and total, and writes a booking under the signed-in UID.
7. Firestore Rules independently compare the rate, currency, and car name to the published car and enforce arithmetic and ownership.
8. Confirmation fetches the newly saved record; it cannot display a random or timer-based success.

This re-fetch and rules check is suitable for demonstrating tamper resistance, but a production rental system would use trusted server logic, transactions, inventory calendars, and payment verification.

## Security design

Public users can query published vehicles only. All car writes are denied to web clients. Users can read their own profile and booking subcollection only. Booking creation requires an exact field allowlist, server timestamps, expected types and bounds, published car existence, EGP currency, matching price snapshots, and `requested` status. Updates preserve every business field and allow only `requested → cancelled` plus a fresh server timestamp. Deletes and unknown paths are denied.

Administrative inventory work is intentionally outside the browser. The local Admin SDK seed script bypasses rules only in a controlled development/production process.

## Demo limitations

Rentora is not a rental operator. It has no real branches, availability, employees, phone support, inventory locking, contracts, payments, insurance workflow, or confirmation process. Prices and pickup locations are illustrative. Contact uses a clearly marked example email. The purpose is to demonstrate a complete, secure student web application flow.

## Five-minute live demonstration

1. **0:00–0:45:** Open Home; explain responsive navigation, Firestore featured cars, and educational disclaimer.
2. **0:45–1:30:** Browse Cars; search “Toyota,” filter categories/prices, sort, reset, and open details.
3. **1:30–2:20:** Start booking; change dates and show UTC calendar-day total updating immediately. Enter invalid dates briefly to show validation.
4. **2:20–3:20:** Continue as a guest, reach checkout, log in/register, return automatically, and send the request. Point out there are no payment fields.
5. **3:20–4:10:** Show the confirmation reference and the matching Firestore record in Emulator UI.
6. **4:10–4:40:** Open account history, refresh to prove persistence, then cancel the request.
7. **4:40–5:00:** Show `firestore.rules`/rules test output and summarize cross-user denial and demo limitations.
